# Routing

In the App Router, folders are routes and special file names are the routing
API. Several conventions changed in 15 and 16 — verify details with
`search_nextjs_manual` before relying on them.

## File conventions

| File | Role | Notes |
|---|---|---|
| `layout.tsx` | UI shared by a segment and its children | Persists across navigation and does not re-render; the root layout renders `<html>` and `<body>` |
| `page.tsx` | Makes the segment a route; its UI | Receives `params` and `searchParams` as promises (15+) |
| `loading.tsx` | Suspense fallback for the segment | Shown immediately on navigation |
| `error.tsx` | Error boundary for the segment | Must be a Client Component |
| `global-error.tsx` | Boundary for the root layout itself | Renders its own `<html>` and `<body>` |
| `not-found.tsx` | UI for `notFound()` and unmatched URLs | |
| `template.tsx` | A layout that remounts on every navigation | Rarely needed |
| `default.tsx` | Fallback for a parallel-route slot | Required for every slot in 16 |
| `route.ts` | Route Handler — exports `GET`, `POST`, … | Cannot share a segment with `page.tsx` |

They nest in a fixed order: `layout` › `template` › `error` › `loading` ›
`not-found` › `page`. One consequence: `error.tsx` sits *inside* its
segment's layout, so it cannot catch errors the layout throws — that takes
an `error.tsx` in the parent segment.

A folder is only publicly routable once it holds `page.tsx` or `route.ts`;
anything else in it can be colocated safely.

## Pages and layouts

Pages and layouts are default exports. A page reads the URL, calls the data
layer, and composes — nothing more:

```tsx
// app/products/[slug]/page.tsx
import { notFound } from 'next/navigation';
import { getProduct } from '@/features/catalog/data';
import { ProductDetails } from '@/features/catalog/components/product-details';

export default async function ProductPage({ params }: PageProps<'/products/[slug]'>) {
  const { slug } = await params;
  const product = await getProduct(slug);
  if (!product) notFound();
  return <ProductDetails product={product} />;
}
```

`PageProps`, `LayoutProps` and `RouteContext` are globally available type
helpers generated by `next typegen` (and by dev/build) since 15.5. On older
versions type props inline — `params: Promise<{ slug: string }>` on 15, a
plain object on 14.

Layouts receive `params` but not `searchParams`, and do not re-render when
navigating between their children — so anything a layout reads can go stale
across navigations. Keep layouts cheap and data-light; do per-request work
in the page or a component inside `<Suspense>`. An `await` at the top of a
layout holds back everything below it.

Metadata comes from a `metadata` export or `generateMetadata` in a layout
or page (Server Components only); `next/head` does nothing in `app/`.

## Dynamic segments

| Folder | Matches | `params` value |
|---|---|---|
| `[slug]` | `/blog/a` | `{ slug: 'a' }` |
| `[...slug]` | `/shop/a/b` | `{ slug: ['a', 'b'] }` |
| `[[...slug]]` | `/shop` and `/shop/a/b` | `{ slug: undefined }` or an array |

Segment values are user input — parse and validate them like any other.
`generateStaticParams` prerenders known values at build time. What happens
to *unknown* values differs by model: without Cache Components,
`dynamicParams` (default `true`) renders them on demand and `false` returns
404; with Cache Components `dynamicParams` is not supported and the page
should call `notFound()` itself. Verify for the project's version.

## Route groups and private folders

- **`(group)`** organises routes without adding a URL segment: give a subset
  of routes its own layout, split marketing from app, or create multiple
  root layouts (navigating between root layouts is a full page load). Two
  groups resolving to the same URL is a build error.
- **`_folder`** opts a folder and its children out of routing — for
  route-private `_components/` or `_lib/`.

## Parallel and intercepting routes

A `@slot` folder renders alongside `children` in the same layout, received
as a prop, with its own loading and error states. Slots are not URL
segments: `app/@analytics/page.tsx` renders at `/`. Since 16 every slot
needs a `default.tsx` (return `null` or call `notFound()`), or the build
fails.

Intercepting routes — `(.)x`, `(..)x`, `(..)(..)x`, `(...)x`, matched
against route segments rather than folders — show a route in the current
context on soft navigation, while a direct load or refresh renders the full
page. With a `@modal` slot, that is the canonical shareable modal:

```
app/
├── layout.tsx                 renders {children} and {modal}
├── @modal/
│   ├── default.tsx            returns null — no modal by default
│   └── (.)photos/[id]/page.tsx    the modal, on client-side navigation
└── photos/[id]/page.tsx       the full page, on direct load or refresh
```

A layout that hides a slot from a user does not stop that slot from
rendering — never use slot switching as authorization
(`references/security.md`).

## Proxy (middleware before 16)

One file next to `app/` (inside `src/` when used): `proxy.ts` exporting
`proxy` on 16, `middleware.ts` exporting `middleware` up to 15. It runs
before routing on every matched request, prefetches included, so keep it
fast and scope it with `config.matcher`.

```ts
// src/proxy.ts
import { NextResponse, type NextRequest } from 'next/server';

const PUBLIC_PATHS = ['/login', '/signup'];

export function proxy(request: NextRequest) {
  const isPublic = PUBLIC_PATHS.some((path) => request.nextUrl.pathname.startsWith(path));

  if (!isPublic && !request.cookies.has('session')) {
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'],
};
```

Use it for redirects and rewrites that depend on the request (locale,
experiments), response headers (a CSP nonce), and optimistic auth redirects
from a cookie's presence. Not for database lookups, slow fetches or real
authorization — the cookie may be forged or expired, and the DAL still
verifies it. Server Actions are POSTs to the page's own route, so a matcher
that excludes a path skips them too.

Runtime differs by version: on 16, proxy runs on Node.js and the runtime is
not configurable (`middleware.ts` remains, deprecated, for edge); up to 15,
middleware defaults to edge with Node.js stable from 15.5.

## Redirects

Pick the tool by when the decision can be made:

| Known when | Tool |
|---|---|
| At build time — a URL moved permanently | `redirects()` in `next.config` |
| Before rendering, from the request (cookie, header, locale) | Proxy — `NextResponse.redirect()` |
| During rendering — missing resource, signed-out page | `redirect()` / `permanentRedirect()` from `next/navigation` |
| After a mutation | `redirect()` in the Server Action, after invalidating caches |
| On a client event | `router.push()` |

`redirect()` and `notFound()` work by throwing. Never call them inside a
`try` block that swallows errors — call them after it, or rethrow.

## Navigation

- `<Link>` from `next/link` for internal navigation, never a bare `<a>`. In
  production it prefetches visible links — dynamic routes only up to the
  nearest `loading.tsx`, so give slow dynamic routes one for an instant
  first paint. Prefetching was reworked in 16; verify details.
- `useRouter()`, `usePathname()`, `useSearchParams()` and `useParams()`
  come from `next/navigation` in Client Components. There is no
  `router.query`, `router.pathname` or `router.events`.
- `useSearchParams()` in a prerendered route client-renders everything up
  to the nearest `<Suspense>` — wrap the component that calls it.
- Server Components read `searchParams` from page props, never from hooks.
- `router.refresh()` re-renders the current route's Server Components
  without losing client state.
- URL state that should not trigger navigation — sort order, an open tab —
  can use `window.history.pushState`/`replaceState`, which `usePathname`
  and `useSearchParams` observe.
